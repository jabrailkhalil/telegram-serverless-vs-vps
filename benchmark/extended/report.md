# Расширенное сравнение Telegram Serverless и двух VPS

Замеры 17 октября 2026 года. Основные выводы: локальная SQLite на обоих VPS быстрее платформенного SQL в выбранных сценариях; синтетический CPU-тест дал сопоставимые времена; выбранный JSON-тест и загрузка одного внешнего файла прошли быстрее из Telegram. Эти результаты не задают общего рейтинга хостингов.

## Что исправлено после первого сравнения

В стенде 10 октября и предварительном прогоне 17 октября SQLite создавалась в /tmp. В Финляндии /tmp оказался tmpfs, то есть RAM, в Германии обычным ext4. Сравнивать устойчивую запись на таких условиях некорректно. Поэтому все финальные операции с базой на обоих VPS повторены в /var/tmp: findmnt подтвердил ext4 на /dev/vda2. WAL и synchronous FULL одинаковы. Это контроль гостевой файловой системы; устройство накопителя и гарантии fsync провайдера не проверялись.

Окончательные числа берутся из results/consolidated.json. Предварительные значения из results/raw.json и segment-*.json не смешиваются с дисковым контролем. Из raw.json использованы завершённые облачные серии и чистые вычисления, на которые расположение SQLite не влияет.

## Среды и границы измерения

| Параметр | Финляндия | Германия |
|---|---:|---:|
| vCPU | 1 | 1 |
| RAM гостевой ОС, MiB | 1963 | 1964 |
| Node.js | 22.23.3 | 22.23.3 |
| SQLite | 3.51.3 | 3.51.3 |
| Хранилище финальной базы | ext4 | ext4 |
| Режим | WAL / FULL | WAL / FULL |
| Load average за минуту перед дисковым контролем | 1,23 | 0,440 |

На VPS продолжали работать существующие приложения. Одинаковый переносимый Linux Node.js запускался в отдельной временной папке; установленный runtime и службы не менялись. На VPS используется node:sqlite, в облаке асинхронный SDK Telegram. Модель сада и SQL одинаковы, изменены имена изолированных таблиц и адаптер. Доступные CPU/RAM, версия SQLite и параметры синхронизации Telegram в этом тесте не установлены. Отделить вклад адаптера, оборудования и хранения по этим данным нельзя.

SQL измерялся вокруг операции внутри исполняемого кода: performance.now на VPS и Date.now в облаке. В облачных SQL-измерениях шаг 1 мс. Внешняя доставка управляющего запроса, холодный старт и появление ответа на экране в эти значения не входят. Проверки выполнялись через аутентифицированный developer run API официального CLI, а не пользовательский endpoint Mini App.

Медиана обозначается p50, p95 считается методом nearest rank. Выбросы сохранены. Ни p95 на коротких сериях, ни минимальное время не являются гарантией сервиса.

## Микротесты базы

Три серии, в каждой 3 прогревочных вызова, затем 50 измерений для коротких запросов или 10 для записи 32 строк. Базовая таблица содержит 1000 пар ключ/значение, вставки получают непересекающиеся ключи. Каждая отдельная запись выполняется без объединяющей транзакции. Вариант с 32 строками использует один INSERT ... VALUES.

В таблицах ниже p50 / p95 в миллисекундах, n указан на одну среду.

| Операция | Финляндия | Германия | Telegram |
|---|---:|---:|---:|
| SELECT 1, n=150 | 0,003 / 0,008 | 0,004 / 0,008 | 2 / 2 |
| Поиск по первичному ключу, n=150 | 0,009 / 0,027 | 0,013 / 0,026 | 2 / 2 |
| UPDATE одной строки, n=150 | 0,613 / 1,03 | 0,507 / 3,82 | 17 / 21 |
| 32 INSERT по одному, n=30 | 18,16 / 32,07 | 95,48 / 96,84 | 533 / 590 |
| Один INSERT на 32 строки, n=30 | 0,690 / 0,986 | 0,534 / 0,767 | 16 / 21 |

Объединение 32 строк снизило медиану Telegram с 533 до 16 мс, примерно в 33 раза. На обоих VPS оно тоже помогает. Нельзя объяснить всю разницу только сетевой ценой SDK: одновременно меняются число SQL-вызовов, отдельных фиксаций и работа базы. Свойства фиксации облака отдельно не измерены.

Разница Финляндии и Германии при серии отдельных INSERT заметна даже на одинаковом runtime. Эти VPS имеют текущую фоновую нагрузку и разные условия ввода-вывода; таблица не доказывает преимущество страны или провайдера.

## Рост журнала сада

Для каждого размера 3 раунда, перед раундом таблица заново заполняется порциями по 1000 завершённых поливов. Чтение: 3 прогрева и 30 измерений; полив: 3 прогрева и 20 измерений. Поливы используют разных синтетических участников и немного увеличивают начальный размер журнала. Чтение агрегирует весь журнал, считает участников и рост.

| Операция | Финляндия | Германия | Telegram |
|---|---:|---:|---:|
| Чтение, 1 000 строк, n=90 | 0,261 / 0,389 | 0,253 / 0,389 | 7 / 8 |
| Полив и состояние, 1 000 строк, n=60 | 0,871 / 1,22 | 0,743 / 1,98 | 22 / 24 |
| Чтение, 10 000 строк, n=90 | 2,05 / 2,8 | 2,16 / 4,19 | 36 / 37 |
| Полив и состояние, 10 000 строк, n=60 | 3,02 / 4,08 | 2,63 / 9,99 | 51 / 54 |
| Чтение, 100 000 строк, n=90 | 22,98 / 27,08 | 22,44 / 30,22 | Ошибка rows_read |
| Полив и состояние, 100 000 строк, n=60 | 23,13 / 28,48 | 22,99 / 40,37 | Ошибка rows_read |

Для 100 000 строк облако успешно заполнило таблицу, но gardenRead, gardenReadNoEnsure и gardenWater завершились ошибкой rows_read во всех трёх попытках каждого сценария. У них нет завершённых измерений времени, n=90/60 в заголовке строки относится только к VPS. Ошибки не заменены нулевой задержкой и не включены в квантили. Это ограничение исходной модели с полным пересчётом истории; хранение счётчиков и готовых агрегатов следует проверять отдельным изменением модели.

В отдельной тестовой копии чтения убран ensurePlanted: повторная попытка создать уже существующий сад. В Telegram медиана на 1000 строк уменьшилась с 7 до 5 мс, на 10 000 с 36 до 34 мс. На VPS стабильного выигрыша этого варианта не получилось. Эта копия использовалась только в benchmark; опубликованный код не менялся.

## Вычисления без базы

В облаке performance отсутствовал, а Date.now возвращал нулевую длительность непустого CPU-блока. Поэтому внутренние нули сохранены только для диагностики. Для сравнения использовано время всего блока, которое вернул серверный run API; на VPS внешний таймер обрамлял такой же блок. Сетевое время контроллера не использовалось. Точная семантика серверного time не документирована в проверенном описании, поэтому это прикладное сравнение блоков, а не изолированное измерение процессора.

CPU: 30 блоков по 20 повторений, каждый делает 2 млн итераций XOR/Math.imul. JSON: 30 блоков по 5 повторений, каждый делает 10 циклов parse/stringify/parse. Входной JSON: 4096 записей, 530 047 байт, создаётся заново в начале каждого блока во всех средах. Контрольные суммы совпали. Прогрев для этих блоков отдельно не удалялся.

Длительность блока делится на количество повторений. Ниже p50 / p95 распределения **средних времён блока на повторение**, не p95 отдельных операций.

| Задача | Финляндия | Германия | Telegram |
|---|---:|---:|---:|
| CPU: 2 млн итераций | 1,92 / 4 | 1,96 / 2,1 | 2,06 / 2,09 |
| JSON: 10 циклов | 29,84 / 37,07 | 34,21 / 47,59 | 11,08 / 12,87 |

CPU получился около 2 мс во всех средах. В этом JSON-тесте Telegram примерно в 2,7–3,1 раза быстрее VPS. На другие размеры JSON, алгоритмы и все приложения результат не переносится.

## Параллельные SQL-вызовы

Уровни 1, 4 и 8, по 5 раундов чтения и прибавления на каждом уровне. На VPS работают worker threads с независимыми SQLite-соединениями; в Telegram Promise.all отправляет SQL-вызовы внутри **одного исполнения функции**. Это разные механизмы конкуренции, их нельзя выдавать за равный тест одновременных пользователей. Время отдельной операции включает её ожидание базы; создание workers в эти времена не входит.

| Операция | Финляндия | Германия | Telegram |
|---|---:|---:|---:|
| Прочитать по ключу, 8 одновременно, n=40 | 0,057 / 1,63 | 0,052 / 0,291 | 2 / 4 |
| Прибавить 1, 8 одновременно, n=40 | 9,23 / 81,93 | 2,65 / 9,95 | 19 / 40 |

Все 65 из 65 прибавлений в каждой среде сохранились, ошибочных результатов завершённых операций нет. При 8 параллельных записях максимальные времена были 106,31, 20,8, 40 мс соответственно. Короткий тест подтверждает сохранность счётчика в этих условиях, но не максимальный RPS.

Предварительная попытка запускать независимые функции через developer API получила HTTP 429 с retry_after. Лимиты управляющего API не являются измерением пропускной способности бот-обработчиков. Паузы и повторные вызовы отражены в предварительных данных, а эта прерванная серия не включена в финальную таблицу.

## Исходящий HTTP и пустой вызов

Из каждой среды последовательно загружались два одинаковых URL, три серии до 10 запросов. Время включает получение тела через text(); соединения могут переиспользоваться. Таймаут Node fetch 15 секунд. После трёх подряд ошибок серия останавливалась. Клиенты разные: Node fetch и SDK fetch. Это проверка конкретных путей к двум ресурсам, а не общей скорости интернета.

| Ресурс | Финляндия p50 / p95, мс | Германия p50 / p95, мс | Telegram p50 / p95, мс |
|---|---:|---:|---:|
| telegram-web-app.js, 30/30 HTTP 200 | 54,17 / 245,62 | 23,28 / 36,47 | 16 / 67 |
| HTML Mini App, VPS 30/30 HTTP 200 | 68,74 / 162,22 | 15,72 / 18,39 | 0/9, fetch: request failed |

URL: [скрипт Telegram](https://telegram.org/js/telegram-web-app.js), [статический HTML Mini App](https://app8881637352.tgcloud.ai/). Успешные тела совпали по длине: 119 731 и 2477 символов соответственно. Ошибки SDK fetch к собственному tgcloud-хосту не означают, что Mini App не открывается. Это другой путь доступа; пользователь подтвердил открытие и полив, приложен [реальный скриншот](../../miniapp-live.png). Причина отказа исходящего SDK fetch отдельно не установлена. Длительности неуспешных запросов сохранены, но не сравниваются со скоростью успешной загрузки.

Для 10 отдельных вызовов функции без базы Telegram сообщил медиану времени исполнения 4,19 мс, а контроллер увидел полный путь developer API 110,22 мс. Это не холодный старт и не задержка бота. На VPS внешний таймер такого вызова дал 0,013 и 0,015 мс; это внутренний runner, без сопоставимого HTTP-транспорта. По этой серии общий пользовательский путь не сравнивается.

## Наблюдаемые границы SQL

Отдельная изолированная таблица без вторичных индексов. Это результаты данного аккаунта на 17 октября, не обещанные публичные квоты.

- Один INSERT на 10 000 строк прошёл; 10 001 получил rows_written limit exceeded. После отклонённого INSERT таблица осталась пустой: частичной вставки в этом запросе не было.
- Два INSERT по 6000 строк внутри одной функции прошли, в таблице 12 000 строк. Ограничение записи наблюдалось на уровне отдельного запроса.
- В таблице из 100 001 строки SELECT SUM(value) WHERE id<=50000 прошёл, id<=50001 получил rows_read limit exceeded. Меньшие проверенные диапазоны тоже прошли.
- SELECT по первичному ключу id=100001 в той же таблице вернул значение. Лимит сканирования не равен максимально допустимому числу записей в базе.

На обоих VPS отдельный контроль корректности через системный Python sqlite3 принял INSERT на 10 000 и 10 001 строку. Версии SQLite этого контроля: 3.46.1 и 3.37.2; он не использован для сравнительных измерений времени.

## Проверка сохранности и файлы

Во всех финальных проверках контрольные суммы совпали; счётчики равны 65; тестовые папки VPS удалены; запрос sqlite_master не нашёл lab_ext_% таблиц в облаке. Настоящий журнал сада содержал 18 поливов до и после. Ревизия и исходники опубликованного приложения совпали с исходным снимком. Проверки и сбор данных не требовали перезагрузки.

- [results/summary.json](results/summary.json): агрегаты, ошибки по сценариям и флаги корректности.
- [results/metrics.csv](results/metrics.csv): числовые ряды агрегатов. pureBlockMean означает распределение средних по блокам; пустые и ошибочные серии не превращаются в числа.
- [results/consolidated.json](results/consolidated.json): выборка финальных фаз с происхождением данных.
- [results/supplement.json](results/supplement.json): дисковый контроль VPS, параллельность, HTTP и пустые вызовы. Последняя служебная проверка в нём получила 429; успешная повторная проверка находится в следующем файле.
- [results/query-boundaries.json](results/query-boundaries.json): границы чтения/записи и окончательная проверка очистки, сада и опубликованного кода.
- results/raw.json, results/segment-*.json: предварительные фазы, включая /tmp и прерванные вызовы developer API. Это архив исследования, не второй набор финальных результатов.
- [README.md](README.md): устройство и повторение тестов.

Стоимость, максимальная нагрузка, долговечность данных при сбое провайдера, задержка Telegram-клиента и холодный старт не измерены. Полный HTTP-бэкенд сада на VPS не разворачивался. Денежная экономия и универсальный выбор платформы из этих чисел не следуют. Для текущей модели с частыми SQL-вызовами VPS быстрее; Serverless сократил работу по размещению бота, базы и интерфейса, а некоторые вычислительные и сетевые задачи выполнил быстрее в выбранных условиях.
